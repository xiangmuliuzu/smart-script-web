## 1. 目标与范围

把运营支撑下 `/support/messages` 的模拟页面替换为真实的消息与公告管理，保留已有指定用户消息的查询、发送与已读详情。公告可以发布给普通用户、后台管理员或两者，接收者有真实的阅读入口与个人已读状态。

普通用户指 `sys_user.user_type` 为 `01/02/03` 的有效登录账号，后台管理员指 `00`。PC 普通用户端与 App 使用同一公告接口，同一用户在两端共享已读状态。公告不是按当前用户名单逐人发送的消息；新注册的用户也能看到仍启用且面向普通用户的公告。

本次覆盖管理页、公告后端与数据库迁移、后台公告阅读入口、PC 普通用户端公告入口和 App 消息中心的最小公告接入。沿用现有视觉样式与依赖。定时发布、角色圈选、短信、外部推送、附件和富文本编辑不纳入本次。

## 3. 方案比较与选择

| 方案 | 成本和行为 |
| --- | --- |
| 扩展现有公告表与服务（推荐） | 一份公告主体，一套阅读记录，按范围读取；兼容历史公告，后台与用户端共用业务规则，新增字段和读取契约较少。 |
| 为普通用户独立建公告系统 | 后台与普通用户两套公告、状态和已读逻辑，同时面向两类账号时需要同步内容，维护成本更高。 |
| 发布公告时逐人创建系统消息 | 可利用现有站内消息入口，但全量发布需要批处理，现有同步接口最多 50 人；新用户不会自动获得此前公告，关闭或修改公告也不能自然影响已投递消息。 |

采用第一种。指定用户消息与公告仍保留独立用途和读取接口，业务页统一承载两者。

## 4. 管理页与消息功能

`/support/messages` 使用真实的 `support/MessagesAnnouncements` 组件，包含“用户消息”和“公告管理”两个页签。页面容器、页头、筛选和表格优先复用现有组件；把消息列表、发送表单、详情拆成可复用模块，旧 `user/message/index` 入口继续使用这些模块，避免两份实现。

用户消息功能：

- 沿用已有类型、创建人、时间区间筛选和服务端分页，不为消息增加未定义的修改、撤回、删除能力。
- 保留系统、审核、交易、权益四种消息类型，标题 200 字、正文 2000 字；业务类型与业务编号必须成对填写。
- 按现有用户查询接口搜索、选择最多 50 名收件人，保留已选用户的标签，并防止旧搜索结果覆盖新结果；选择器查询仍遵守 `user:app:list` 权限。
- 请求编号由前端生成并内部保留，正常操作不要求用户填写技术字段。失败重试使用相同编号和同一提交内容；内容变化后重新生成编号，避免把不同内容错误当成等价重试。
- 发送期间禁止重复提交；成功展示真实收件人数并刷新列表。失败保留表单内容；对结果不确定的网络故障允许等价重试。
- 详情展示正文、业务关联、发送人、时间、收件人数及脱敏收件人列表，以现有 `readAt` 展示每位收件人的已读状态；未返回实际投递状态的字段不展示虚构的成功率。
- 列表、远程搜索、详情分别有加载、空数据、错误及重试状态。

## 5. 公告字段与生命周期

复用 `sys_notice`、`sys_notice_read`，只为公告主体新增接收范围字段：

| 字段 | 契约 |
| --- | --- |
| `noticeId` | 现有公告主键。 |
| `noticeTitle` | 现有标题，去除首尾空白后必填，上限 50 字符。 |
| `noticeType` | 保留现有 `1` 通知、`2` 公告。 |
| `noticeContent` | 必填，采用纯文本多行输入及预览，本次约定上限 5000 字符。 |
| `audience`（新增） | `USER` 普通用户、`ADMIN` 后台管理员、`ALL` 两者；新增表单必须明确选择，默认选择后台管理员。 |
| `status` | 保留现有 `0` 启用、`1` 关闭。关闭时接收者不可查询及阅读，也不计入未读；不引入第三种草稿状态。 |
| `createBy/createTime/updateBy/updateTime` | 保留现有元信息，由后端维护。创建时间展示为创建时间，不伪装成独立的发布时间。 |

公告管理支持标题、类型、范围、状态筛选和真实分页；新增、编辑、内容预览、启用、关闭、删除。新增默认关闭，允许“保存”或明确“保存并启用”；状态改变和删除需要普通业务确认。

已启用公告可修改标题与正文，但接收范围必须先关闭再调整，避免在编辑时意外扩大传播范围。关闭后重新启用、编辑内容均保留原个人已读记录；如需再次提醒所有人，创建一条新公告。删除公告与清理已读记录在同一事务中完成。

旧公告迁移为 `ADMIN`，保留原状态和内容，不自动向普通用户公开。历史 HTML 不在浏览器或 App 中直接执行；阅读时转为安全纯文本，保留可读段落。新公告按纯文本存储，避免把正文当作 HTML。

## 6. 接收者规则与阅读入口

公共公告服务统一计算可见范围。后台账号只能阅读启用的 `ADMIN/ALL` 公告；普通用户只能阅读启用的 `USER/ALL` 公告。接收者身份由已认证的服务端身份上下文取得，客户端不能通过传 `userId` 或 `audience` 扩大阅读范围。

- 后台管理员：在顶部增加公告按钮、个人未读角标和阅读抽屉，支持分页、详情、单条已读、全部已读。阅读资格不依赖公告管理权限，因此没有发布权限的管理员也能阅读发给管理员的公告。
- PC 普通用户：在现有“消息与沟通”中增加“平台公告”页签，支持分页、详情和已读操作；公告未读单独标识，并计入公共消息角标总数。通知、会话、公告任一统计失败时继续沿用现有不完整统计降级规则，不显示误导性的完整合计。
- App：在现有消息中心增加公告入口/页签，复用本次 App 凭证域读取接口与相同已读契约，补齐加载、空态、错误重试与返回后刷新。
- 成功加载详情后再尝试标记已读；读取失败不写已读。已读请求失败保留未读状态并允许重试。所有未读数统计全部当前可见公告，不受当前页或顶部 5 条限制。
- 单条、批量、全部已读必须在 SQL/服务层限定当前账号及当前可见的启用公告；不可见、关闭或不存在的公告按不存在处理。重复阅读保留首次已读时间。

## 7. 接口与权限契约

### 7.1 现有管理契约

保留 `/api/v1/admin/notifications` 的列表、详情、创建接口及 `user:message:list/query/add` 权限。接收人搜索使用现有 `/api/v1/admin/app-users` 和 `user:app:list` 权限。

保留 `/system/notice/list`、`/system/notice/{noticeId}`、`POST /system/notice`、`PUT /system/notice`、`DELETE /system/notice/{noticeIds}`。公告管理使用原 `system:notice:list/query/add/edit/remove` 权限，列表增加 `status/audience` 的真实服务端过滤，写入增加范围、枚举、正文非空与长度校验。状态更新使用现有编辑契约，服务端独立执行全部业务约束。

### 7.2 拟新增接收者读取契约

| 方法 | 后台账号读取 | 普通用户读取（PC/App 共用） | 用途 |
| --- | --- | --- | --- |
| GET | `/system/notice/received` | `/api/v1/announcements` | 当前账号可见公告分页。参数 `pageNum/pageSize`，按公告 ID 倒序。 |
| GET | `/system/notice/received/{noticeId}` | `/api/v1/announcements/{noticeId}` | 当前账号可见公告详情，不自动写已读。 |
| GET | `/system/notice/received/unread-count` | `/api/v1/announcements/unread-count` | 当前可见启用公告的全部未读数 `{total}`。 |
| PUT | `/system/notice/received/{noticeId}/read` | `/api/v1/announcements/{noticeId}/read` | 幂等标记单条已读，返回 `{changed}`。 |
| PUT | `/system/notice/received/read-all` | `/api/v1/announcements/read-all` | 幂等标记当前账号全部可见公告已读，返回 `{updated}`。 |

后台返回若依 `TableDataInfo/AjaxResult`，用户端返回现有 `AppApiResponse<PageResult<…>>`，客户端按已有请求适配器解包。分页默认每页 10，上限 100。列表返回 `noticeId/noticeTitle/noticeType/createTime/isRead`；详情追加安全纯文本 `noticeContent`。普通用户响应不包含管理者账号、内部备注或管理权限信息。

App 安全链和相关异常处理的路径范围需纳入 `/api/v1/announcements/**`，要求有效 App Access Token；不得新增匿名读取或混用若依管理员令牌。后台接收者接口要求真实 `00` 管理员身份，不能仅凭传入参数认定身份。

历史 `/system/notice/listTop/markRead/markReadAll` 如继续保留，也必须统一执行后台身份与可见性规则，修正未读数量口径，不能成为绕过接收范围的旧接口。

### 7.3 菜单与授权

菜单 `5152` 保留现有路径、位置与入口权限，更新为真实组件。原用户消息菜单 `3010` 保留兼容入口，本次不调整用户中心的其他菜单。

在 `5152` 下恢复/登记公告管理所需按钮权限，初始化 SQL 的最终菜单树不能被前面的系统菜单精简再次删除。普通受限角色不会因新增菜单自动获得全部发布或删除权限；保留其原消息授权，公告授权按显式角色菜单绑定处理。

实施补充：增加隐藏的 `/support/announcements` 接收者页面，不加入侧栏、不授予管理权限。没有任何业务菜单的管理员也能进入布局，通过顶部入口阅读面向后台的公告。

页签按查询权限展示，按钮按对应写权限展示；仅有入口权限但没有任一列表权限时给出无可用功能提示，不调用会返回 403 的列表。消息发送与用户选择权限缺一时给出清晰的权限提示。

## 9. 验收与验证

1. `/support/messages` 显示真实列表，发送、查询、公告保存及状态操作实际落库；不显示模拟 KPI 或成功提示。
2. `USER/ADMIN/ALL` 三种公告的列表、详情、单条已读、全部已读、未读统计严格符合接收范围；猜测 ID 和调用历史接口也不能跨范围读取或写已读。
3. 关闭公告立即从接收者查询和未读数中消失；重新启用保持已读；删除同时清理阅读记录。历史公告仅后台可见。
4. 新注册用户可以看到启用的用户公告；同一普通用户在 PC 与 App 的已读状态一致。不同用户阅读互不影响。
5. 超过 5 条或超过一页的公告，角标仍显示完整未读数。全部已读只影响本人可见公告。
6. 无管理权限的后台账号能阅读后台公告；无对应按钮权限不能发送、修改、删除。非管理员的用户令牌不能访问公告管理接口。
7. 指定用户消息继续遵守最多 50 人、字段长度、业务引用成对、等价重试不重复创建的现有规则；搜索和详情请求乱序不覆盖新状态。
8. 空白正文、非法范围/类型/状态、超长字段由前后端校验；历史 HTML 与恶意内容不会执行。加载失败能重试，提交失败能恢复表单。
9. 用有行为意义的后端测试覆盖范围隔离、状态与已读幂等，用 Web 测试覆盖受影响的未读合计、请求幂等和路由映射；运行 Web `npm run gate` 及相关后端测试/编译。App 做相关静态分析和公告数据解析/交互校验；未执行的真机联调如实记录。
