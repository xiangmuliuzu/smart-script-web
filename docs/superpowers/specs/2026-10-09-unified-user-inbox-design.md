# 通知与公告统一收件箱

用户于 2026-10-09 明确确认：App 和 PC 用户端合并站内消息与平台公告，公告归入系统分类；公告管理取消通知/公告类型区分。沿用消息与公告已获批准的身份、范围、已读、纯文本和状态规则，不变更数据归属或增加外部推送。

## 实现契约

1. 接收端只保留一个通知列表，沿用全部、系统、审核、交易、权益分类。公告归为 `SYSTEM`，与指定用户通知按创建时间倒序排序，服务端统一分页并返回全量总数。
2. 扩展已有 `/api/v1/messages`、`/unread-count`、`/read-all` 的可选参数 `includeAnnouncements=true`；默认不传时保留既有通知行为。客户端启用合并读取；详情和单条已读仍复用原消息/公告接口。
3. 合并列表行增加内部来源 `source=NOTIFICATION|ANNOUNCEMENT`，`messageId` 为对应来源的编号。界面不呈现内部来源。前端列表键、详情与已读依据来源及编号，允许两表同编号同时显示。
4. 公告查询只返回当前有效普通账号可见的启用 `USER/ALL` 公告；消息只返回当前账号的未删除收件行。全部已读在一个事务中处理本人可见的两类记录。未读总数及系统分类计数包含公告，但不能重复累加。
5. App 删除双页签，公告在系统分类展示，详情路由携带内部来源用于准确读取。PC 用户端删除平台公告页签，通知列表包含公告；沟通会话仍有独立入口。后台管理员阅读入口仍接收后台公告。
6. 公告管理删除类型筛选、类型列和类型选择。新建/保存的公告使用既有 `noticeType=2`；历史类型 `1` 继续可读，统一显示为公告，不删除旧记录或阅读状态。
7. 不新增框架或数据库表。验证混合排序/分页、同编号、分类、个人未读和全部已读隔离、历史通知兼容及已有接收刷新行为；完成后重建并覆盖安装到现有模拟器，保留应用数据。
