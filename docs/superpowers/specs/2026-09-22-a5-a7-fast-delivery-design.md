# A5–A7 快速交付标准调整设计

## 背景

A1–A4 采用了完整契约、测试矩阵、多轮独立复审和合并后回归流程。该流程提高了完备性，
但显著降低了功能开发速度。项目负责人决定从 A5 到 A7 临时切换为“功能优先、测试后补”，
当前阶段只以功能可运行和相关仓库基础构建通过作为阻塞门禁，安全与完整测试在后续集中加固。

本决定是 2026-09-22 的负责人书面决策，其优先级高于现有《A用户与认证开发规格》和
《A用户与认证评审验收标准》中针对 A5–A7/G5–G8 的旧要求；`rules.md` 中的技术栈、
分支保护、先设计后编码和人工确认要求继续有效。

## 目标

- 缩短 A5、A6、A7 从需求到可运行功能的交付周期。
- 将阶段阻塞条件收敛到功能主流程、基础构建和最小敏感信息底线。
- 保留原详细要求作为后续加固清单，避免删除后遗漏。
- 让开发者和评审者能够明确区分“快速阶段通过”和“最终安全加固完成”。

## 非目标

- 不改变既定技术栈、三仓边界、数据库版本或 Git 分支规则。
- 不授权直接向 `release` 推送；仍由项目经理通过 PR 合并。
- 不把未执行的自动化、安全扫描或回滚演练表述为已通过。
- 不追溯降低 A1–A4 已完成阶段的验收标准。

## 规则调整

### 1. A5–A7 当前阻塞门禁

每个阶段只要求同时满足以下条件：

1. 本阶段承诺的功能主流程已经实现，并能在开发环境实际运行。
2. 每项核心功能至少完成人工正常路径冒烟，记录入口、操作和结果。
3. 受影响仓库通过基础构建：后端完成跳过测试的 Maven 打包，Web 完成生产构建，
   Flutter 完成静态分析和可用目标的调试构建。
4. 后端和前端能够启动，新增主流程不存在已知阻断错误。
5. 提交中不得出现已知明文密码、Token、验证码、数据库口令或实名材料地址。

阶段允许带着已登记的非阻断问题和未补测试进入下一阶段。

### 2. 延期但不删除的要求

现有 G5–G8 详细检查项全部保留，但统一移动到“A5–A7 后续加固清单”，当前不作为
PR 合并、阶段通过或 A7 发布准备的阻塞条件，包括：

- 完整自动化测试矩阵、异常与越权场景穷举、跨端兼容矩阵。
- 漏洞扫描、全量敏感信息扫描、生产配置安全核验。
- 数据库备份、迁移、回滚与恢复演练。
- 无跳过/无 flaky 证明、完整证据包和独立评审复现。
- 所有加载、空、错误、重试、无权限和会话失效状态的自动化覆盖。

延期项只能标记为“待加固”或“未执行”，不得标记为通过。

### 3. 阶段定义

- A5：实现 App 用户中心承诺的页面和正常业务路径，App 与涉及的后端基础构建通过即可进入 A6。
- A6：提供统一身份上下文并至少接通一个 B/C/D/E 示例主流程，相关仓库基础构建通过即可进入 A7。
- A7：完成可运行版本、部署所需基础说明和 release PR；在基础构建与人工主流程冒烟通过后，
  可按项目经理决定进入发布流程。原 G8 安全与硬门禁转入后续加固。

### 4. 状态表达

阶段记录采用以下结论：

- `快速阶段通过`：满足当前功能优先门禁，但后续加固未完成。
- `不通过`：功能主流程不可运行、基础构建失败、应用不能启动，或发现明文敏感信息进入提交。
- `最终加固通过`：后续重新执行原 G5–G8 详细要求并完成评审后使用。

不得用“快速阶段通过”替代最终安全完备性声明。

## 验证方式

本次只修改 Markdown 文档，完成后执行：

1. 搜索 A5–A7/G5–G8 的旧阻塞表述，确认没有与快速交付条款冲突。
2. 检查两份文档的版本、优先级、阶段退出条件和结论术语一致。
3. 检查不存在 `TBD`、`TODO`、空白责任人或把延期项写成已通过的表述。
4. 复核 `rules.md` 中技术栈、分支保护和人工确认规则未被覆盖。

## 后续加固触发方式

负责人另行确认开始加固后，再依据保留的 G5–G8 清单建立专项计划。加固工作可以分批完成，
但只有原详细安全、数据、兼容和测试门禁全部关闭后，才能登记为“最终加固通过”。
